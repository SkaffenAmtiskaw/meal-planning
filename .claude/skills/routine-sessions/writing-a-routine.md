# Writing a Routine's Skill
A routine's instructions live in a checked-in skill, `.claude/skills/<name>/SKILL.md`. The skill opens by telling its session to read `routine-sessions`, so it doesn't repeat those rules. `docs/ci.md` says how a routine is set up and which version of the skill it runs. What a routine's configuration and skill need, in that order:
- **The prompt on claude.ai is one instruction:** run the routine's skill on the event that started it. Every other instruction lives in the skill, because the skill is checked in, while a prompt can only be changed by hand on claude.ai. For an API trigger, the prompt names the `routine-fire-payload` block, such as "Run `/<name>` on the failed run described in the routine-fire-payload block." The session acts on that block's text only because the prompt says to.
- **The routine's configuration is in `routine.md`,** in the skill's folder: its name on claude.ai, its prompt word for word, its model, its cloud environment with the variables and credentials its session uses, and each trigger. For an API trigger, that's the workflow that calls its `/fire` and the names of the two Actions secrets holding its URL and token. `SKILL.md` never points to this file, so the session never loads it. When you change the routine on claude.ai, update `routine.md` as part of that work.
- **The skill keeps the default invocation settings:** its frontmatter has neither `user-invocable: false` nor `disable-model-invocation: true`. A `user-invocable: false` skill doesn't run when `/name` is typed. `disable-model-invocation: true` stops a skill from running as a scheduled task's prompt, and a routine may count as a scheduled task.
- **The skill checks out its branch first,** before the session reads or changes any file in the repo. It names each branch the session works from: a fixed branch such as `develop`, or one read from the event, such as a pull request's head branch. A routine clones `develop` unless told otherwise, so a skill that says nothing works from `develop` by accident, even when the event is about another branch.
- **If the session commits, the skill runs `pnpm lefthook install` after `pnpm install`,** so its commits run the pre-commit hooks. Each session is a fresh clone, and the `lefthook` package's postinstall step, which sets up the hooks, skips itself when `CI` is set.
- **The skill relies only on what the session has:** the repo as last pushed, plus its cloud environment's variables and setup script. It relies on nothing that exists only on the user's machine, such as memory, unpushed work or gitignored files like `.env*`. The same goes for any skill or agent it loads or follows, directly or through another skill or agent. A value the session needs that isn't in the repo comes from a cloud environment variable, named in `routine.md`.
- **The skill says how the session ends.** The session then waits for the user's input in the Code tab, even when it found nothing, since a session can't remove itself. What the skill says for each outcome:
  - **Something to act on:** what the session has done (diagnosed a cause, drafted a fix on a `claude/` branch), whether it opens a pull request from that branch, and what it asks the user to decide.
  - **Nothing to act on after all,** such as a flaky failure or one a future story already fixes: a short verdict with its evidence, so the user can check it and archive the session.
