# Sorting an E2E Failure
A failing spec may only be out of date with a change the pull request meant to make. That's yours to fix. Otherwise the app may be broken, and every fix to the app goes through the bug workflow, which reproduces, plans and reviews it. The cases, in order:
- **The spec is out of date:** a commit on the pull request changed the behavior the failing assertion checks, and the change was meant. The change was meant if the commit's message says so, or if the story the commit names says so, which you read in the notes clone. Fix it as step 4 of `SKILL.md` describes, updating only the spec.
- **Anything else, or you aren't sure:** hand the failure to the `root-cause-analyst` subagent, which runs on a stronger model than this session and writes a root cause for the user to review. Give it the command as you reproduced it, such as `pnpm test:e2e` with any variable you set, its output, the pull request's commits as a range from its base branch to the failed commit, and the notes clone's path. The code clone may hold only `develop`, so fetch the base branch first. What to do depends on its report:
  - **Its verdict is that the test is out of date with an intended change:** fix it as step 4 describes, with the report as your diagnosis.
  - **Anything else:** make no fix to the E2E failure and open no pull request for it. If another failed job's script also failed, fix that one first as step 4 describes. Leave `pnpm test:e2e` out of the scripts you run there, since it still fails and `fixing-a-failure.md` would send you back to diagnose it. Then, if the head branch has a newer commit, run the command on it the way you reproduced the failure. What to do depends on the result:
    - **It passes:** a newer commit has already fixed the failure, so name both commits in the summary you stop with, and show no report.
    - **It fails, or there's no newer commit:** copy the whole report into the summary you stop with, as the analyst returned it, under a line saying `root-cause-analyst` wrote it. The user reviews the analyst's own claims and evidence, and a subagent's result stays hidden in the session unless they expand it. After the report, offer to create a bug note from it.

## The Bug Note
If the user asks for the bug note, create it in `features/<area>/` in the notes clone, from `.claude/note-templates/Bug.md`. Its Symptoms name the failing spec, the pull request and the failed run, and its Root Cause holds the report. Add its Roadmap line as the `roadmap-placement` skill describes. Commit both, push them, and give the user the commit's link.
