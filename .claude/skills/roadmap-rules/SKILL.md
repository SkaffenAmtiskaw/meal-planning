# How the Roadmap Works
How goals order the work, what each section and kind of note holds, and the rules for lines:
- **Goals** - ranked epics, each a note in `goals/` in the notes repo, shaped with `/shape-goal` and ranked with `/roadmap`. Only the user changes the order. Only one goal is built at a time, so `develop` never holds another goal's unfinished work and a finished goal releases all at once:
	- **The building goal** is the top one, marked `- building`. Once its last line and the last 🔁 line have closed, its release shows after that marker: ` · Next: /finish-goal`, then ` · releasing` once `/finish-goal` starts its audits, then ` · releasing · Next: /ship-goal` once the stories its goal note's `# Release` section links have closed. What may be built (`/implement`, `/infra-build`, `/tooling`) depends on the line's marker and whether a release is under way:
		- **If the story's line has 🔥:** it may be built in every case below, because it's built on a `hotfix/` branch from `main`, and the release freeze covers only `develop`.
		- **If its line under Goals includes ` · releasing`:** only the notes the goal note's `# Release` section links, which are its audits, their fixes, any Done When gaps `/ship-goal` found and any dated copy started for a problem the release caused. Holding everything else back keeps out work that the release neither planned for nor caused.
		- **If a PR from `develop` into `main` is open:** nothing, until it merges, since `/ship-goal` has already closed out the release's goal.
		- **Otherwise:** a line in Bugs waits until a release picks it up. Any other story or collecting-note item is built only when it serves the building goal, serves no ranked goal, or has 📌 or 🚨 on a line in Now or Next.
	- **The planning goal** is the second, marked `- planning`. Its stories can be shaped, decided, designed and planned down to steps, but they aren't built until the building goal is released. Collecting notes aren't kicked off for it. Once `/ship-goal` closes out the building goal, the planning goal's line ends with ` · Next: /roadmap once the release PR merges`, so the Roadmap shows what starts it building.
	- **The rest** organize the backlog. Their lines sit under their headings in Later, and their stories can be shaped and decided ahead of their turn.
- **Standing Goals** - listed under their own subheading below the ranked goals, because they're never ranked, building or planning. A goal drawn from one is ranked like any other.
- **Roadmap Instructions** - a goal or standing goal can hold instructions under its Roadmap Instructions heading, in any wording, for any skill that works with goals or places Roadmap lines. When you work with a goal or standing goal, read its instructions and follow each one that applies to what your run is doing. An instruction is the user's decision, so ask only if you can't tell what it wants or when it applies. If the user asks for a new instruction during a run, write what they meant under the goal note's Roadmap Instructions.
- **What joins every release** - sweeps, collecting workflow notes and bugs rarely fit a goal, so if they waited for one they might wait forever. So when any goal starts building, `/roadmap` kicks off every sweep and collecting workflow note and moves every bug line into Next. A sweep item can be blocked by a story in this release, meaning the story's line is in Now or Next. Such an item joins the release in a copy of its own, which waits for the story through `blocked-by`, so the sweep's other items don't wait. Other blocked work waits for the next release. The goal ships once this work is done too.
- **Now** - in progress.
- **Next** - the building goal's queue, in order. Every line that serves the building goal and isn't in Now sits here, so the goal's whole scope shows in one list. The first line not waiting on anything is the next one to plan or build. A line that's waiting keeps its place, and its status embed says what it waits on. A 🔥 line sits first, because its fix ships to production without waiting for any release. While a release is under way, the lines its goal note's `# Release` section links sit right below any 🔥 line, so the release's own work is built ahead of the rest.
- **Planning** - the planning goal's queue, in order. Every line that serves the planning goal and isn't in Now or Next sits here, so the user can plan the goal from one list. The first line not waiting on anything is the next one to plan. When the planning goal starts building, its lines move into Next in the same order.
- **Bugs** - bugs in the shipped app, security issues included, waiting for the next release. They belong to no goal, because they're just work that needs doing. The section comes right after Planning, because the next goal to start building, normally the planning goal, picks them up. Until then, a bug can be shaped, investigated and planned down to steps, so it's ready when its release starts, but it isn't built. A bug in a story still being built belongs to that story, and one in dev tooling or CI belongs to Dev Tooling. Code that works but needs changing belongs to App Health. How an urgent bug skips the wait depends on where its fix has to land:
	- **If its fix can ship with the building goal's release:** it gets 🚨, moves into Next and is built on `develop`.
	- **If it has to reach production before then:** it gets 🔥 and moves to the top of Next, as a hotfix.
- **Later** - committed, not ordered. One heading per goal below the planning goal, in rank order, then one per standing goal, then **Collecting Notes** for every collecting note's own line. The building and planning goals have no heading, because their lines sit in Next and Planning. A line that serves more than one goal sits under one of their headings and ends with a `🎯 [[Goal]]` link for each other goal. A re-rank doesn't move it to another heading, because the 🎯 links, not the heading, say which goals it serves. Dev tooling and agent work sits under Dev Tooling's heading unless the user says it serves a ranked goal.
- **Uncommitted** - every story line that serves no goal, other than bugs and collecting notes, however ready its note is. Serving a goal, standing goals included, is what commits the user to a story. Bugs and collecting notes don't need one, because they join every release. A line with 📌 is committed wherever it sits, so its 📌 alone doesn't move it. A line moves out once it serves a goal, to where its goals put it.
- **Numbering** - Goals, Next and Planning are numbered lists whose numbers run 1, 2, 3 in order, because a line's number is how the user reads its place. So when you add, move or remove a line in one of them, including moving a line into Now or deleting its note, renumber every one of these lists the edit changed.
- **Status embeds** - each line with a note, except a goal's or standing goal's, embeds that note's status line from Where It Stands after the link, e.g. `[[Stale Data Issues]] ![[Stale Data Issues#^status]]`. It shows only what the story needs next, the next skill or a link to what blocks it, not what the story is. Edit it in the note, not on the Roadmap.
- **Length** - a line says what its work is in 100 characters or fewer, not counting its markers, so the Roadmap reads at a glance. Work that needs more becomes a note with a short line linking to it, as the `filing-work` skill describes. A marker's reason, such as a 📌 or 🚨 reason, or a note the user added to the line can take it past 100, up to 250 characters in all. Keep each of those to a few words.
- **Markers** - every Now and Next line ends, after its status embed, with a marker: a 🎯 link for each goal it serves, one of them the building goal, or 🚨, 🔥, 📌 or 🔁. Every Planning line ends with a 🎯 link for each goal it serves, one of them the planning goal:
	- `🎯 [[Goal]]` - serves that goal.
	- `🚨 <reason>` - something serious enough to show on the line, such as a security risk or a bug a user reported. In Now or Next, the story is built ahead of the goals. Anywhere else, it only flags the problem, and the story waits its turn.
	- `🔥 Hotfix: <reason>` - a bug in production that can't wait for the release. The story is built on a `hotfix/<slug>` branch from `main` and ships on its own, as "A Hotfix" in `docs/branching.md` describes. It never gets 🔁 or a 🎯 link, and a goal that starts building leaves it where it is, so it never joins a release and closing it never sets off `/finish-goal`.
	- `📌 <reason>` - the user scheduled it outside the goals. Only the user adds it. Where the line sits says which release it joins:
		- **In Now or Next:** it's in this release, so it may be built now.
		- **Anywhere else,** such as Later or Uncommitted: it joins the next release. When a goal next starts building, `/roadmap` moves it into Next, and it keeps its 📌.
	- `⏸️ <reason>` - the user is holding the line back until its reason no longer holds, such as a library that doesn't work with the dev tooling yet. Only the user adds or removes it. While the reason holds, the line stays out of Next and Planning and isn't built, whatever goal it serves.
	- `🔁` - joined this release without belonging to a goal: a bug, a dated copy of a sweep or collecting workflow note, or a `/tooling` change. It's added when the line moves into Next.

	If an agent's skill sets out a case for adding 🚨 or 🔥, the agent adds it in that case. Otherwise, only the user adds them, and an agent may suggest one. Both markers move a story ahead of the goals' work, which is the user's call.

	A Now, Next or Planning line without its marker is out of place. Raise it with the user.
- **Hubs** hold shared design, not priority. A hub has a line only while it has a next step of its own, such as `/brainstorm`, `/decide` or `/close`. Once its `^status` line says `Next: its child stories`, it has none.
- **Archived notes** have no line while an open story still relies on them. Once none does, an archived note gets a line until `/close` deletes it.
- **Collecting notes** gather items until they're handled together: sweeps (`type: sweep`) for small, decided fixes that share a group, such as Unit Test Tidy-Ups, and collecting workflow notes for tooling and agent changes, such as Agent Workflow Changes. If several related items have their own lines on the Roadmap and no collecting note covers them, tell the user they could become a new collecting note. Leave creating it to them, because every collecting note joins every release.
	- **The note's line** carries no 🎯 links, because a collecting note keeps getting new items, so it never finishes. A kickoff freezes some of its items into a dated copy, `<note> YYYY-MM-DD`, which can finish, and the note keeps collecting.
	- **A collecting note's items** have no goal links, because they join whichever release comes next.
