A redesign of the desktop meal detail modal (the one that opens when you click a meal on the
calendar). It now matches the rest of the app: the same header, footer and dish markers as Add
Meal. Notes can be edited in place, there are Move to / Duplicate actions, and there's a full edit
mode that reuses the Add Meal layout.

> **Build Order: Implement this AFTER the [[Unified Date Picker Component|unified date picker]]**.
> Move to, Duplicate and the edit-mode Date field all use that picker. Nothing here should be built with a temporary or native date input.

![Read view](assets/meal-detail-modal/01-read-view.png)

### Read view
What you see when you open a meal.

**Header**
- A small square in the meal's color, then the date in long form ("Thursday, September 24").
- Meal name as the title (20px, bold).
- The description underneath, if there is one. No description → nothing rendered.
- Close button top right.

**Dishes**
- Section heading "DISHES" with the count ("4 dishes").
- Each dish is one row: a marker, the name, a source line, and the note.
  - **Marker:** filled green dot = saved recipe; hollow green ring = reference (URL, or book and
    page); light grey dot = no source. The same marks as the Add Meal chips.
  - **Name:** green and linked when there's a source; plain navy when there isn't.
  - **Source line:** after the name, in small italic. "Saved recipe" for a saved one, or the
    reference text itself.
  - **Note:** its own line in full navy, never truncated, author line breaks kept. Same rules as
    the list-view dish notes handoff. No note → nothing rendered.
- Rows are evenly spaced, whether or not they're linked. (The current modal spaces linked and
  plain dishes differently.)

**Footer action bar**
- Left: **Move to…** and **Duplicate…** (quiet green text buttons).
- Right: **Edit meal**, an *outlined secondary* button with a pencil icon, deliberately not
  orange. Nothing has changed yet, so it shouldn't look like a submit button. Orange is only
  used when committing a change (Save note, Save changes).

### Inline note editing
![Inline note edit](assets/meal-detail-modal/04-inline-note-edit.png)

Each dish row has a small button on the right: **Edit note** (solid outline) if it has a note,
**Add note** (dashed outline) if it doesn't.

- Clicking it swaps the note line for a textarea with **Cancel** and **Save note** (orange).
- Only one dish is edited at a time; opening another closes the first.
- Saving updates the row immediately. Saving an empty note removes the note line.
- Only notes can be edited here. Name and source changes go through Edit meal.

### Move to / Duplicate
![Move to picker](assets/meal-detail-modal/02-move-to-picker.png)

  - The meal is **today**: *Tomorrow* / *Next week*.
  - The meal is on **any other day**: *Next day* / *Week later*.
  - The meal is **in the past**: a shortcut only shows if it lands on today or later; if neither

- Past dates stay selectable.

![Moved, with Undo](assets/meal-detail-modal/03-moved-with-undo.png)

## Design from Add Meal Changes (Saved Recipes)
The design handoff below is generated by Claude Design. It has been reviewed and approved by the user, but it is very detailed and the user may forget details in it (or she might change her mind). If there is a conflict between the design handoff and the user's instructions, you should prompt the user for clarification.

The design handoff should be treated as a source of truth (except in the case of user conflict) for the UX/UI. It should not be a source of truth for implementation details. Mantine boundaries are a best guess not a binding contract. Clean architecture and component design are more important than trying to preserve the design handoff's approach.

Follow-up to [[Add Meal UX Changes]]. The two-pane modal, collapsible dish row and mobile sheet from that handoff stay. This one changes **how a dish gets its saved recipe**, and adds a tag filter.

### What's wrong today
A mobile tester couldn't find how to add a saved recipe. The path is *Add source → Saved →
picker*: three taps deep, behind a chip labelled for how we store the data rather than what
people are trying to do. When shown where it was, they said they'd never have looked there.

People think "add the curry I saved", not "add a dish, then give it a source". Saved recipes need
to be the first thing you see when adding a dish, not an option buried inside it.

### The change
- **Desktop:** a third column, **Saved recipes**, is always on screen next to the dishes. You can
  browse, search and filter it by tag, and add a recipe as a dish in one click.
- **Mobile:** no room for a column, so the dish name field doubles as a search. **Add dish** adds a
  row with your saved recipes already listed under it.
- **Both:** the source picker (None / Saved / Reference) is gone. A dish has a saved recipe, a
  reference, or nothing, and the row shows which.

### 2. Dish row (both)

`[ name ] [ recipe chip ] [ note chip ] [ expand arrow ] [ delete ]`
(Mobile puts the name and delete on one line, and the chips and arrow on the line below.)

#### Recipe chip
| State | Look | Tap |
|---|---|---|
| Empty | Dashed outline, grey hollow ring, **"Link recipe"** | Starts linking (desktop: link mode, §3; mobile: opens the saved list, §4) |
| Saved recipe | Solid outline, **filled green dot**, recipe name | Opens/closes the expand panel |
| Reference | Solid outline, **hollow green ring**, URL or book text | Opens/closes the expand panel |

A long label drops `https://`, stays on one line with an ellipsis, and shows in full on hover.
The chip never wraps.

#### Note chip
Dashed **"Add note"** when empty, solid **"Note"** when set. Tapping it opens or closes the expand
panel. While the row is closed, the note shows as a line under it (one line with an ellipsis on
desktop, wraps on mobile).

#### Expand arrow
Opens and closes the panel. Points down when closed, up when open. Several rows can be open at
once.

#### Delete
Trash icon. Uses the app's **existing delete confirmation modal**, and the row is removed once
confirmed. Hidden when only one dish is left.

#### Expand panel
![Desktop Expanded Rows All Tags](assets/calendar-add-meal/03-desktop-expanded-rows-all-tags.png)
![Mobile Row Expanded](assets/calendar-add-meal/06-mobile-row-expanded.png)
Desktop: two columns (Recipe | Note). Mobile: stacked.

- **RECIPE**, with a saved recipe linked: the recipe name (wraps, never cut off), then text
  actions **Change** (starts linking again) and **Remove** (unlinks; the row keeps its name).
- **RECIPE**, with nothing linked: a filled green button **"Link a saved recipe"**, then the helper
  "or add a reference", then a text field (placeholder "URL, or book and page").
- A dish has **either** a saved recipe **or** a reference. Linking a saved recipe clears the
  reference.
- **NOTE:** a textarea (placeholder "Prep reminders, swaps, what to buy…").

### 3. Saved recipes column (desktop)

#### What's in it
Every recipe and bookmark in the planner, the same set as the Recipes page. Each result shows
the name, its kind in muted text (**Recipe** / **Bookmark**), its tags as small colored badges,
and an action button on the right.

#### Order
**Most recently used on a meal first**, then alphabetical. See *Data change* below.

#### Search
Matches anywhere in the name, ignoring case. Works together with the tag filter (a result must
match both). If nothing matches: "No saved recipes match."

#### Browse mode (default)
![Desktop Layout](assets/calendar-add-meal/01-desktop-browse.png)
- **Add** (outlined pill) adds a new dish at the end of the list, named after the recipe and
  already linked to it.
- **A recipe can be on a meal only once.** Recipes already on this meal show a muted
  **"Added"** that does nothing.

#### Link mode
![Desktop Linking](assets/calendar-add-meal/02-desktop-linking.png)
Starts from an empty **Link recipe** chip, **Change**, or the panel's **Link a saved recipe**.

- The dish being linked gets a light green tint and green border.
- A banner at the top of the column reads **"Linking to *Dish name*"** with **Cancel**.
- The search is **prefilled with the dish's name** and **any selected tags are cleared**, so an
  old filter doesn't hide the likely match.
- Every action button becomes a filled green **Link**. Recipes already on the meal still show
  "Added".
- Picking one links it to that dish, **keeps the dish's name** (or uses the recipe's name if the
  dish is unnamed), leaves link mode and clears the search.
- **Cancel** or **Esc** leaves without changing anything. Deleting the dish being linked also
  leaves link mode.

### 4. Search-as-you-type (mobile) — `05-mobile-type-ahead-open.png`, `07-mobile-tag-selected.png`
![Mobile Typeahead](assets/calendar-add-meal/05-mobile-type-ahead-open.png)
![Mobile Tag Selected](assets/calendar-add-meal/07-mobile-tag-selected.png)

- **Add dish** adds an empty row and immediately opens its saved list, titled **"RECENTLY USED"**
  (top 5).
- The name field's placeholder is **"Dish name or search saved recipes"**, which says outright
  that it searches.
- **Typing** filters the list, retitled **"FROM YOUR SAVED RECIPES"**. With tags selected, the

- Each result: green dot, name, kind, tag badges, **Use**. Tapping a result fills in the name,
  links the recipe and closes the list.
- The last row, **"Add "*typed text*" as a new dish"**, closes the list and keeps what was typed.
  Before anything is typed it reads "Type a name for a new dish" and does nothing.
- **Editing the name of a linked dish unlinks it.** It's now a different dish.
- The list reopens when the name field is tapped, or from an empty Link recipe chip, **Change**, or
  **Link a saved recipe**. Only one row's list is open at a time.
- Tag chips sit in a single row that scrolls sideways.

### 5. Tag filter (both)

Shown above the results: the library column on desktop (wraps), the search list on mobile
(scrolls sideways).

- **Selected tags must all match.** A recipe has to carry every selected tag to show.
- **Selected tags come first**, filled with the tag's own color from the planner palette. Tap to
  turn one off. **"Clear"** appears when any are selected.
- **Only tags that would return something are shown**: tags carried by at least one of the
  current results (search + selected tags). Tags that would return nothing are hidden, not
  greyed out.
- **Most used first.** Unselected tags are ordered by how many *current results* carry them;
  ties go to whichever is used more across the whole planner. That count shows in muted text
  after the name and updates as you narrow.
- **Six shown at a time**, selected ones included. The rest sit behind a dashed **"+N more"** that
  shows them all and turns into **"Fewer"**.
- Picking a tag moves the keyboard highlight back to the first result.

---

### 6. Keyboard (desktop)

In the library search field:

| Key | Does |
|---|---|
| ↓ / ↑ | Moves a highlight through results (white background, thin green outline) |
| Enter | Runs the highlighted result's action: **Add**, or **Link** in link mode |
| Esc | Clears the search and highlight; in link mode, also leaves link mode |

- The highlight moves back to the first result whenever the search or tags change. Hovering with
  the mouse moves the same highlight, so the mouse and keys never point at two different rows.
- Every result can be reached with Tab; **Enter** or **Space** runs its action. "Added" results
  can be focused but do nothing.
- A one-line hint under the tags shows the keys: **"↑↓ move · ↵ add · Esc clear search"**, or
  **"↑↓ move · ↵ link · Esc cancel linking"** in link mode.
- Tab order: meal fields → each dish row (name, recipe chip, note chip, arrow, delete, then panel
  fields) → Add dish → library search → tags → results → Cancel → Add Meal.

### 7. Saving
- Date and Meal name are required. **Add Meal** stays disabled until both are filled.
- Dishes with no name are dropped on save and don't count toward "N dishes on this meal".
- Saving a meal updates **last used** on every saved recipe it links (see below).

### Styling
Same palette and tokens as the previous handoff. The new bits:

- **Saved recipes column:** chalk tint (same as the Meal column), divider on its left. Section
  label "SAVED RECIPES" is small, bold, uppercase, spaced out, muted navy.
- **Link-mode banner:** light forest background with a forest border, navy text with the dish name
  in bold, forest **Cancel** text button.
- **Linking dish:** forest border with a very light green fill.
- **Action pills:** *Add* is white with a light forest border and forest text; *Link* is filled
  forest with white text; *Added* is muted grey with no border.
- **Tag chips:** pill-shaped. Unselected: white, light border, a small dot in the tag's color,
  the name in navy, the count muted. Selected: filled with the tag's background, border and text
  colors from the tag palette, no count. "+N more"/"Fewer" is a dashed forest pill.
- **Tag badges on results:** smaller pills with the tag's background and text colors, no border.
- **Filled dot = saved recipe, hollow ring = reference, grey ring = nothing linked.** Same meaning
  on chips, results and the panel. Don't add the words "(recipe)"/"(bookmark)" to chips; the result
  list already shows the kind.
- Contrast rule from the last handoff still applies: interactive labels, counts beside tags, helper
  lines and the key hint all need 4.5:1 or better.

### Likely Mantine boundaries
Starting points only. Use whatever fits the codebase best.
- Modal (desktop) / full-screen modal (mobile), with a grid for the three columns
- `TextInput` with a search icon for library search; `ScrollArea` for the independent scroll areas
- Chip or Badge for tag filter chips, reusing the existing `Tag` component for result badges
- Button (outline / filled / subtle) for Add, Link, Added
- Combobox, or the existing search-as-you-type pattern, for the mobile name field
- Collapse for the expand panel; ActionIcon for the arrow and delete

### ⚠️ Data change — required
**Saved recipes and bookmarks need a new "last used" date.** Set it whenever a recipe or bookmark is linked to a dish on a saved meal. It drives the "Recently used" order in the library and the mobile search list. Recipes that have never been used sort after used ones, alphabetically.

Nothing else in the data changes: dishes still store a name, an optional saved recipe or
reference, and an optional note.

### Handoff: Mobile — List view

### Overview
The list view currently renders a **"Coming soon" placeholder** on phones. This story replaces it
with a real mobile list: one continuous vertical scroll of days, each day a section header followed
by its meal cards. It is the same idea as the desktop list view, re-laid-out for a narrow screen —
the desktop's fixed left date gutter and hover-revealed controls do not survive on touch.

Like the desktop list view, **there is no meal detail modal here.** Everything a cook needs — meal
name, description, every dish, its recipe link or book reference, and its prep note — is on the row.

This story covers the **list view on mobile only**. The mobile month view is a separate story and a
separate handoff.

### Fidelity — Mantine first, pixels second
**Build this out of Mantine components and props. That matters more than matching the prototype
pixel for pixel.** The sizes, spacings and colors below are design intent, not a contract. Where a
Mantine component, prop, theme token, or spacing step gets you close, take the Mantine version —
`Stack`/`Group`/`Divider` over styled `<div>`s, `Card`/`Paper` over hand-rolled borders,
`ActionIcon`, `SegmentedControl`, `Affix` over custom equivalents, `c="navy"` over a hex literal,
`size="sm"` over a `fontSize`, `gap="xs"` over raw margins. Something a few pixels off but built
from real Mantine primitives and theme tokens is the **correct** outcome; a pixel-exact version
built from inline styles and hardcoded hexes is not. Reach for custom styling only where Mantine
genuinely has no answer.

Two things are not negotiable to taste:
2. dish notes sit on their own line, are never truncated, and carry full-strength ink;
3. all primary content clears 4.5:1 contrast — the muted ramp is only for the labels named in the
   Accessibility section.

The prototype (`Mobile List View.dc.html`) is a look-and-behavior reference built outside the app.
Do not port its markup, inline styles, or fixture data.

- A hairline rule fills the space between the label and the action on the right.

  touch. It opens the add-meal flow with that day's date prefilled, and needs an accessible name

**Meal card** — one per meal, stacked under the day header:
- Left rail in the meal's tag color (4px), otherwise a plain bordered card on white.
- Meal name; optional description beneath it, muted.
- **Dish list** — one line per dish with a small bullet:
  - plain dish name; or a link when the dish has a saved recipe or an external URL (external links

  - an optional book/page reference after the name, small and italic, muted;
  - the dish's **note on its own line beneath the name**, full-strength navy ink, wrapping to as

**Empty day:** the day header stays, followed by a single quiet line — "No meals planned", in the
muted ink at a smaller size (this is real information, so it must not drop below the muted ramp's
`navy.4` — do not go lighter). The day's add button in the header is the affordance; no second
large empty-state block per day. Empty days must keep their height so the scroll rhythm is even.

#### 4. Floating "Add Meal" button
Persistent, bottom-right, ember, above the scroll. Defaults to today's date (or the topmost visible
day — pick one and be consistent). The scroll region needs bottom padding roughly the height of the
button plus its margin so it never covers the last card.

### Interactions & behavior
- **Initial position:** on open, the list is scrolled so **today's section is at the top** of the
  scroll region, with a small offset above it. No animation on first paint.
- **Today:** smooth-scrolls back to that same position.
- **Scroll → header label:** the month/year label reflects the topmost visible day section and
  updates as the user scrolls.
- **Date picker:** choosing a date scrolls that day's section into view (extending the loaded range
  if the date falls outside it).
- **Day add button / floating button:** open the existing add-meal flow with the date prefilled.
- **Dish link tap** navigates to the recipe or external source and must not trigger anything behind
  it.
- **Range:** a fixed window around today (roughly two weeks back, three weeks forward) is enough
  for this story. Infinite scroll in both directions is a follow-up, not part of this design.
- **Read-only users** (no write permission): no floating button and no per-day add buttons; empty
  days simply read "No meals planned".
- **Loading:** skeleton day sections — header line plus one card-height block. Do not collapse the
  scroll height.
- **Empty range:** if nothing loads at all, the standard empty state. Individual empty days are
  normal and are not an error.

### Breakpoint
This treatment applies at the existing mobile breakpoint for the list view (the one currently
gating the placeholder). Above it, the desktop list view with its date gutter is unchanged. The two
implementations should not both mount.

### Accessibility
- The list is a semantic list of days; each day section is labelled with its full date.
- Per-day add buttons and the floating button have accessible names that include the date.
- Touch targets ≥44px (the 28px circular add glyph needs a larger hit area than its visual size).
- Today is identified by more than color — its date label reads as today's date and should be
  announced as such, not left to the tint alone.
- **Contrast, scoped:** all primary content — meal names, dish names, dish notes, "No meals
  planned" — clears 4.5:1. Dish notes in particular use **full navy ink**, not the muted `navy.4`
  grey (≈2.8:1 at this size): with no detail modal the note is primary content, and it reads as
  secondary through size and weight, not through fading.
- The theme's muted ramp is used **only** for labels that are decorative or redundant with content
  available elsewhere: the day section label (the full date is in each day's accessible name), the
  meal description, and the book/page reference. These sit below 4.5:1 by design. If one of them
  turns out to be the only place a piece of information appears, it moves to full navy rather than
  staying muted.
