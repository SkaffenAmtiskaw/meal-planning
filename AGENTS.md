# Agent Instructions

## Project
A full-stack meal planning web app. Work is planned and tracked as notes in the Obsidian vault in the `meal-planning-notes` repo beside this one, and `sh scripts/notes-dir.sh` prints its path. Obsidian Git commits and pushes that repo, so a local session never does.

## Following Instructions
The user wants instructions followed for what they're for, not to the letter. If a case matches a line's words but not its point, or following it would make no sense, work out what the line is for and do that. Bring it to the user only if the case still conflicts with that purpose, because a question about a case the line was never meant for gives them nothing to decide. Before you pass on a subagent's finding that cites a line, judge it the same way.

## Working with the User
- **When to ask.** Whether you ask depends on what a choice affects:
  - **A piece other code will call or copy,** such as a hook's API or a component's props: if no approved plan settles it, design it as "Every New Piece Sets a Precedent" in `docs/project_conventions.md` describes, and make the call, even when it has more than one reasonable shape. Name it in your summary as a precedent: show its API and how a caller uses it, and say which existing code it follows. If it departs from that code, also name the code you moved over to the new way. If moving some of it would be out of proportion to the change, name the code still to move instead. Later code copies the piece, and a change is cheapest now.
  - **What the app does or shows, what tooling, CI or a routine does for the user, or architecture:** if there are two reasonable options and nothing written picks one, ask.
  - **Only a low-level detail,** such as a command's flags, or how code is organised: where a file or helper goes, how code is split or what something is called. Make the call and name it in your summary, because the user doesn't want to decide these. Don't mark it as their call or write it down as a rule unless breaking it would cause a real problem, as "Problems You Find" describes, because a later session would then have to work around it or ask.
- **Questions.** If a turn ends waiting on the user, end it with the question in the next-step box, as `wrap_up`'s `ask` with reply buttons. The box is how they notice a session is waiting. Use AskUserQuestion only in the middle of a turn, for a short choice whose full context fits in the dialog, because it hides the chat text and the user doesn't see its option previews.
- **What the user sees.** Anything the user needs to read, such as a draft to approve, a finding or a token to paste, goes in the turn's last message, after its last tool call. In a turn that ends with a question, that's the message after `wrap_up`. Text you write before a tool call reaches them only as a sentence or two of summary, however short it is. That's a known bug in how the model API returns that text (anthropics/claude-code#74558), and you can't see it happen, because your own copy of the turn still holds the full text. So never point them to text "above" from earlier in the turn.
- **Plain words.** Whenever you bring the user something to decide or read, such as a question, a draft, options, a finding or an out-of-scope item, open with what it's about in plain words: what goes wrong or what would change, and for whom. Name a file, function or rule only after that, with a few words on what it is, and leave out other terms that only a draft, a note, a subagent's report or this session uses. The user knows the app and the workflow, not every name in the code, so anything that opens with a name leaves them working out what it means before they can decide. A subagent's report or a note's text uses its own terms, so restate what you take from it rather than passing its wording on.
  - **If it's a draft to approve or options to choose from,** such as a design, a Convention or a plan: after the plain-words account, show each decision the draft or option makes on a real case from this project, and say what the decision does with that case. The user approves what they understood a draft to say, so a dense draft lets a major part of it get past them. Pick a case they could reasonably expect to go the other way, because a case where the decision and their reading agree can't show them the difference. For example, for a rule that a type lives with the module that owns it, show a type imported from several folders, and say that it stays with the module that owns it rather than moving to the lowest folder those importers share. In a long draft, the plain-words account is the summary, and each case goes with the part it shows.
  - **If it involves code,** such as an approach, a new piece or a choice between two shapes, whether or not it's also a draft: also show the code, after the plain-words account and with the case it handles, because the user follows an implementation from its code more readily than from a description. Show enough around the change to see where it runs and what it works with, such as the component that calls a new hook, and show a change to existing code as a diff, because a line cut off from where it runs leaves the user without the context to judge it. Say what the code does and why in sentences beside it. Keep comments to what a comment would say in the committed code. A reader takes in a line of code before its comment, so a reason in a comment arrives after the line it was needed for. Call each folder and piece by its name, not an abbreviation or a number, because each stand-in is one more term to hold in mind.
- **Buttons.** Make every button in the next-step box a reply button, meaning a `wrap_up` button with no `action` field. For a commit, that's one labelled "Commit" rather than the commit action. A reply button sends its label, so the user knows what they're sending. An app-action button sends the app's own text, which can say more than the label.
- **Recommendations.** If the user asks for one, give one. Otherwise, give one when best practice supports it, and name the practice. When a choice comes down to their preference, say so.
- **Reasons for an option.** Base them on the work itself, such as how its pieces depend on each other, how hard it is to review and test, or what it does for the app's users. Unless the user has raised timing, never base a reason on when something ships, lands or gets fixed, or on where it sits on the Roadmap. They own the release schedule and the order of work.
- **Approval.** What happens to a change depends on whether the user has settled it, whether it's a small fix, and its length:
  - **If they've settled its exact form, or it's mechanical:** make it and name it in your summary, even where a skill has an approval step, because approving what they've decided costs a review and adds nothing. A change is mechanical when it follows from one already made and leaves the meaning unchanged.
  - **If it's a small fix, as "Problems You Find" describes:** make it without asking. The table of changed files is enough.
  - **If it's short:** show them the code or wording they haven't seen, as "What the user sees" describes, and ask whether they approve.
  - **If it's long:** do the same, but show a summary and a table of the changes, and show the text only for the parts they ask to see, because they miss things in a long draft.
- **When the user changes an earlier choice.** They've already decided, so record the change without asking about the earlier one or warning them. If the choice is in the note you're working on, update it there. If it's in another note, add an Inbox item to that note, as the `editing-notes` skill's "The Inbox" describes, because that note's own skills make the change.
- **When an earlier choice bears on your work.** The user's choices, including the conventions, designs and plans they approve, count only through their reasons. So before you rely on one, check that it still holds, meaning that what it rested on still applies. That goes for shaping your work around it and for arguing from it against an option, even one the user asks about. A choice stops holding in two cases. One is when the simplest way to do the work conflicts with it: keeping it means adding code, steps or special cases the work wouldn't otherwise need, even if each one looks small. The other is when new information changes what it rested on, such as a tool they didn't know about or a choice made since. For example, a choice to ship a migration alone, so that a rewrite needs no compatibility code, stops holding once the rewrite needs a migration of its own. When either happens, deal with the choice as soon as you see it, rather than working around it or arguing from it. A design built around a choice that doesn't fit keeps growing, while the choice itself is quick to change. Arguing from it steers the user away from an option that may now be the better one.

  A low-level detail isn't the user's call, even one marked as theirs. Any other choice is their call if "When to ask" says to ask about it, or if they've shown it matters, such as by giving a reason of their own or writing it themselves. A story's scope, meaning the work its note takes on or leaves out, is their call too. What you do depends on whose call it is:
  - **If it's the user's call:** say in a sentence or two what no longer works, and ask whether you can do X instead. X can be an option they rejected earlier, if what ruled it out has changed. If they agree, update the choice as "When the user changes an earlier choice" describes, and carry on.
  - **Otherwise:** change the choice, as "When the user changes an earlier choice" describes for the note it's in, and name the change in your summary.
- **Unchecked facts.** If your work rests on a fact nobody has checked, such as how a library or the built app behaves, settle it at the earliest point anything can show it. That includes a fact a note or an earlier step left unverified. A fact that turns out wrong in a later step sends the work back to design. The cases, by what it takes to show the fact:
  - **If it needs something only the user has,** such as knowledge of their own setup, their sign-in or their judgment: if they might know it offhand, such as how a GitHub setting is set, ask them. If they wouldn't, or don't, walk them through the check as "What only the user can do" describes, and run the parts that don't need them yourself.
  - **If nothing can show it until a later step builds something:** leave it to that step's check, and say why it can't be settled sooner.
  - **Otherwise:** find it out yourself, by reading the code, the built output or the docs, or by running a command or the app. A check you hand the user waits until they get to it, so the work stalls.
- **What only the user can do.** If work needs setup outside the repo or a check only they can do, walk them through it at the point it's needed, one step at a time, and wait for them before the next. A list of setup at the end of a summary reads as reference, not as a prompt to act. How you hand over each step:
  - **Its actions:** give each one its own list item with a bold header, such as "1. **Merge the PR:** ..." then "2. **Run this command:** ...". On 2026-11-07 the user missed an action buried in a paragraph and ran the next command too early.
  - **What it proves:** for a check, say after its actions what they should see and what that proves.

  Whether you hand them a step now or draft one into a note for a later session, never send them to a file in a worktree, because working in a worktree is a pain for them. If a worktree needs a value they supply, such as a key in `.env.local`, have them add it to the main checkout's copy. Then copy it over yourself.
- **New-session cards.** Whether you put up a new-session card with `start_session` or give the user a command to type depends on what the card would bring:
  - **If your skill says to put up a card:** do as it says.
  - **If the new session needs something the typed command can't give it,** such as the user's complaint in their own words: put up the card.
  - **Otherwise,** such as `/place-design <note>` after `/design-feature`: give the user the command to type in a new session, because a card would bring nothing the command doesn't. A card can also fail. On 2026-11-10, a session started from a card couldn't run a skill that sets `disable-model-invocation: true`, as most planning skills do. Its prompt arrived as plain text, so the command didn't expand, and the Skill tool refused the flagged skill.
- **A problem's size.** If the user says a problem is large or keeps coming back, work from that size rather than arguing it down, because agents have kept offering narrow fixes while the user had to insist on a large-scale change. If it's outside the session's work, record their account of its size in its out-of-scope item. Otherwise, work out where it comes from and propose the fix that would end it, even if that means replacing what's there.
- **Security risks.** If a risk you or a subagent found could reach production, or the story is about that risk, raise it. Otherwise, leave it out, along with any hardening against it. Dev tooling that runs on the user's machine against their dev database is the usual case, because at worst it reaches dev data.
- **Doc gaps.** If you notice something that belongs in `docs/`, what you do depends on whether the session can edit the code repo:
  - **If it can't,** such as a session in the main checkout: put the facts on the out-of-scope list, meaning what the docs miss or get wrong, where, and why it matters. Don't draft the fix, because triage first checks whether a note or Roadmap line already covers the gap, and the session that takes up the routed item drafts it and settles it with the user.
  - **If it can:** deal with the gap right then, because this session can edit the docs, and docs that wait for later rarely get updated. What you do depends on the gap:
    - **A wrong or out-of-date rule with one right fix, in a doc this story already edits:** it's a Boy Scout fix, as the `triaging-out-of-scope-work` skill describes, so don't ask.
    - **Anything else:** raise it and offer to draft it now. If the user wants it later, add it to the Docs Updates note.
- **Summaries.** If you changed files and your skill's report doesn't list them, your summary includes a table, so the user can open each file. Give each file a row, or each group of files with the same change. A row holds the file as a markdown link and a one-line description of its change.

## Notes
Before you change a note in the notes repo, invoke the `editing-notes` skill. These rules hold for every session:
- **Embedded sections** (`![[Note#Section]]`) are part of the note. A raw file shows only the link, so open each one.
- **Links to a heading or block** (`[[#^piece-7]]`, `[[Note#Section]]`) point to content the line depends on, so read the target when that line matters to your work.
- **The user's lines:** a line where their name is a tag or a signature (`[Sarah] I want X instead.`, `Change this to Y - Sarah`) is their own words. Never edit one or write in their voice.
- **Roadmap order** is the user's call, so never reorder `Roadmap.md` in the notes repo.
- **Uncommitted stories:** a story whose Roadmap line sits in Uncommitted without 📌 may never be built, so never rule out, hold back or reshape other work because it might get in the way of one. You can still propose work that overlaps one, on that work's own merits. If built work changes something an uncommitted story relies on, handle its note as you would any other, as the `editing-notes` skill's "The Inbox" describes.
- **⚠️ Check Drift callouts:** only `/check-drift` adds one or changes its finding, because each records a finding `/check-drift` settled with the user. Another session may still fix a link or a name in one, as in any other line, and remove one when its skill says to.
- **A Roadmap line with no note:** remove the line only once its work's PR merges, because until then the work isn't on `develop`. Hold the removal as held notes work, as `opening-the-pr.md` and `waiting-for-the-merge.md` in the `building-code` skill's folder describe. When you remove the line, follow step 3 of the `deleting-a-note` skill.
- **Held notes work at session start:** if the session-start output names a merged PR with held notes work, tell the user and put up a new-session card for the main checkout that runs `/tooling #<PR>`. Do nothing else about it, because the new session does that work.
- **Before you finish** a session that changed a note, run `sh scripts/vault-lint.sh "<note>" …`, naming each note it changed. Fix what it reports in those notes. Tell the user about anything it reports in other notes, because another session may be working on them.

## Problems You Find
Whether you, a subagent or a check found a problem, first make sure it's real: that the code and notes bear it out, and that it's a problem with what the user actually meant rather than with a misreading of it. A subagent states a problem that isn't real as confidently as one that is. If it's real, what happens to it depends on whether it matters:
- **If leaving it would cause a real problem,** such as a bug, a failing or flaky test, a security risk that could reach production, lost data, code a later change would struggle with, or work that goes against a story's Purpose or a choice that's the user's call: it matters, so bring it to the user as your skill describes. A doc gap is handled as "Doc gaps" describes.
- **Otherwise, it's small,** such as a tidy-up, an inconsistency or a wording fix. If it needs no decision and sits in a file your work already changes, fix it without asking the user or reporting it as a finding: now, or, if a later step of the story's plan edits the file, as a Boy Scout fix in that step, as the `triaging-out-of-scope-work` skill describes. Otherwise, drop it, with no note, out-of-scope item or mention.

Each problem that reaches the user costs them a decision, and a small one isn't worth it, now or in a later session.

## Out-of-Scope Work
Keep a running list of anything that looks outside the story or step you're working on and matters, as "Problems You Find" describes. Also list anything that would add a piece or a question to a story that's already been through `/shape`. Unless the user puts an item forward for the work, as below, don't stop to deal with it as it comes up, because it would pull the session away from its work.

What you do with something the user raises depends on what it is:
- **Work they put forward for what you're settling with them,** such as a tool to try or a case to cover: whether it's part of the work is their call, not yours. So if it looks outside the work, say why at that point and ask whether to pull it in. Asking at triage is too late, because by then the work has been settled without it. If they leave it out, put it on the list and note that they did, so triage only routes it.
- **Feedback on how a skill, subagent or the workflow behaves,** when this session isn't working on that same skill or subagent:
  - **If an agent did something it shouldn't have, or didn't do what it should,** in this session or another: offer `/debrief`, even if you've already put this case right. `/debrief` works out whether the cause could come back, and fixes it if so. Leave the feedback off the list, whether or not the user takes the offer, because the offer is where they decide whether to deal with it.
  - **Otherwise,** such as a capability they'd like added: put it on the list, even when it's also saved as a memory.
- **Anything else,** such as a problem they point out in passing: put it on the list.

Before you show the user the result they approve, triage the list, as the `triaging-out-of-scope-work` skill describes. Then route what's left, as that skill describes.

## Subagent Reports and Scratch Files
Unless the user can't open the session's files, such as in a routine's cloud session, save each subagent's report, unedited, in `.scratch/`, so the user can open it whole. Write the file from the text the subagent returned to you. A background subagent's `.output` file is its transcript, not its report. It also sits outside the session's folders, so reading or copying it prompts the user. When you show the user the subagent's findings, put them in the chat, as "What the user sees" describes, and link the report if you saved one. Each commit deletes the files in `.scratch/` that haven't been written to for a day, so anything a later session needs goes in the note you're working on. A note never links to a scratch file.

## Docs
Read a doc in `docs/` when the task needs it, not all of them up front. Each is named for what it covers. These have triggers their names don't show:
- `project_conventions.md` and `project_structure.md`: before planning or writing any code
- `style_guidelines.md` and `theme.md`: before UI work
- `ci.md`: also before changing a routine
- `seed.md`: also before adding a model
- `release_tasks.md`: before planning or writing a change that needs production's stored data changed, such as a model's new or changed fields
- `branching.md`: before work that touches branches, worktrees, PRs, releases or hotfixes

Before you plan, draft or change a file in `docs/`, `README.md`, AGENTS.md, a skill or an agent, read the `writing-standard` skill.

## Library APIs
The libraries here are newer than your training data, so never use an API from memory. Every API you use needs a source, depending on the case:
- **If this codebase already uses it:** use it the same way.
- **If it's a Mantine component you're using for the first time or for a new purpose:** read its page, found through https://mantine.dev/llms.txt, because the types don't show how it's meant to be used.
- **Otherwise:** the docs or type definitions for the installed version. Next.js's docs are in `node_modules/next/dist/docs/`, and better-auth's start at https://better-auth.com/llms.txt.

## Commands
The commands that need explaining:
- `pnpm test:agent <path>` runs the tests for a file or folder, with coverage and output made for agents. Use it instead of calling `vitest` directly.
- `pnpm lint` writes fixes to the files. `pnpm lint:ci` only reports, as CI does.

## Git and Files
- **Checkouts:** planning sessions run in the main checkout, which stays on `develop` and is never edited, so the SessionStart hook can keep it on the latest `develop`. Every change to the code repo is made in a worktree session on its own branch, and reaches `develop` through a PR, because `develop` accepts nothing else.
- **Archiving:** a worktree session holds its worktree, and that worktree's slot, until it's archived. Archiving hands both to the next new session, which checks out its own branch in that folder. So once a worktree session has nothing left to do, offer to archive it with `archive_session`. If some of its work waits on its PR's merge, such as held notes work, offer once that work is done. Otherwise, offer without waiting for the merge.
- **Commits:** commit only this session's files, by path, since other sessions' changes may be staged too. When you commit depends on the branch:
  - **If it will be merged:** commit when they ask, or when they give an approval that a skill's steps say commits, usually its final approval of the work. When you ask for that approval, say that approving commits, and if it's the final approval, say so, such as "Final approval: is Step 3 done? Approving commits it." Label its reply button "Approve and commit". The user often approves a draft or part of a change that isn't ready to commit, so any other approval commits nothing.
  - **If it's a throwaway that will never be merged:** commit and push freely, since nothing on it reaches the app.
- **Changes you didn't make:** the user often runs several sessions at once and edits notes by hand. What you do depends on when you find one:
  - **When you commit:** if it doesn't look like another session's work, ask about it.
  - **When you need to edit a note that has one:** what you do depends on whether your edit overlaps or conflicts with the change:
    - **If it leaves the change's lines as they are and doesn't undo what it did,** such as an edit to another section or to the line next to them: make it. An edit made from the note's current text keeps the other change, and Obsidian Git commits both together.
    - **If it would change, move or remove those lines, rewrite the whole note, or undo what the change did, such as by writing a link under the name the change replaced:** don't make it, because whoever made the change may still be working on it. Tell the user what edit the note needed.
  - **When you're about to delete a file that has one, or an untracked file that isn't yours:** ask first, because git can't bring it back.
- **Checks:** if the user hasn't asked you to, don't edit the config that sets the repo's checks, such as `biome.jsonc` or `lefthook.yml`, or add a comment that switches off a check. Getting past one error that way loosens the check or hides the error. If they ask for an ignore comment, put it on that one line only.
- **Memory:** a project rule lives in a checked-in file, because memory exists only on the user's machine and other agents never see it. Memory holds how to work with the user and how outside services behave. Once a rule is checked in, delete the memory that carried it.
